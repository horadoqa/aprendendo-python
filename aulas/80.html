Arquitetura de software

Nesta aula vamos conhecer conceitos fundamentais de arquitetura de software. À medida que nossos projetos crescem, colocar todo o código em um único arquivo começa a gerar problemas. A arquitetura ajuda a organizar o sistema em partes bem definidas, facilitando a manutenção, os testes e a evolução do projeto.

🎯 Objetivo da aula:

Aprender como organizar aplicações Python utilizando camadas, serviços, repositórios e conceitos de Clean Architecture.

🏗️ O que é arquitetura de software?

Arquitetura de software é a forma como organizamos as diferentes partes de uma aplicação e definimos como essas partes se relacionam.

Em projetos pequenos, podemos começar com poucos arquivos. Porém, conforme a aplicação cresce, separar as responsabilidades se torna cada vez mais importante.

💡 Uma boa arquitetura ajuda a:

• Organizar o código.
• Separar responsabilidades.
• Facilitar os testes.
• Reduzir acoplamento.
• Facilitar manutenção.
• Permitir evolução do sistema.

🧱 1. Camadas

Uma estratégia comum é dividir a aplicação em camadas.

Cada camada possui uma responsabilidade específica.

Interface
↓
Serviço
↓
Repositório
↓
Banco de dados

Por exemplo:

  • Interface: recebe requisições.
  • Serviço: executa regras de negócio.
  • Repositório: acessa os dados.
  • Banco: armazena informações.

⚙️ 2. Serviços

A camada de serviços normalmente concentra as regras de negócio da aplicação.

Por exemplo, imagine um sistema bancário. A operação de sacar dinheiro possui uma regra:

Saldo suficiente?
↓
Sim → realizar saque
Não → rejeitar operação

Essa regra pode ficar dentro de um serviço.

services/conta_service.py

class ContaService:
     def __init__( self, repository):
         self.repository = repository
     def sacar( self, conta_id, valor):
         conta = self.repository.buscar( conta_id)
         if conta.saldo < valor:
             raise ValueError( "Saldo insuficiente")

Observe que o serviço não precisa saber exatamente como os dados são armazenados. Ele apenas utiliza o repositório.

🗄️ 3. Repositórios

🧹 4. Clean Architecture

A Clean Architecture é uma abordagem para organizar sistemas de forma que as regras importantes da aplicação fiquem independentes de detalhes externos.

A ideia central é reduzir o acoplamento entre as regras de negócio e tecnologias específicas.

Regras de negócio
↓
Casos de uso
↓
Infraestrutura

Podemos imaginar a aplicação como círculos.

🌐 Interface

⚙️ Infraestrutura

📦 Casos de uso

🧠 Regras de negócio

Quanto mais importante for a regra de negócio, menos ela deve depender de detalhes externos.

🔗 Regra de dependência

Um dos conceitos fundamentais da Clean Architecture é a Dependency Rule.

As dependências devem apontar para dentro.

A regra de negócio não deve depender diretamente de banco de dados, framework ou interface.

Por exemplo, em vez de fazer a regra de negócio depender diretamente do PostgreSQL, podemos depender de uma abstração.

🧩 Interfaces e abstrações

💉 Injeção de dependência

O serviço pode receber o repositório por parâmetro, em vez de criá-lo internamente.

class UsuarioService:
     def __init__( self, repository):
         self.repository = repository
     def buscar_usuario( self, usuario_id):
         return self.repository.buscar( usuario_id)
💡 Vantagem:

Podemos trocar a implementação do repositório sem precisar alterar a regra de negócio.

🚀 Projeto prático

Agora vamos imaginar um pequeno sistema de cadastro de usuários.

O sistema deverá permitir:

  1. Criar usuários.
  2. Buscar usuários.
  3. Atualizar usuários.
  4. Remover usuários.
  5. Validar regras de negócio.

Podemos dividir o projeto da seguinte maneira:

Controller → recebe a requisição

Service → executa as regras

Repository → acessa os dados

Model → representa o usuário

⚠️ Não complique sem necessidade

Arquitetura não significa criar dezenas de arquivos apenas para deixar o projeto mais sofisticado.

Um projeto pequeno pode não precisar de todas essas camadas.

💡 Regra prática:

Comece simples.

Conforme o sistema cresce, extraia responsabilidades quando isso realmente trouxer benefícios.

Desafio — Sistema de produtos

  2. Um repository para armazenar produtos.
  3. Um service para aplicar regras.
  4. Uma camada responsável pela interface.
  5. Testes para o service.
