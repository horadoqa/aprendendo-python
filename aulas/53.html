Projeto: API + PostgreSQL + Autenticação

Nesta aula, vamos colocar em prática vários dos conceitos estudados até agora criando uma pequena aplicação completa. O projeto terá uma API REST, banco de dados PostgreSQL, operações de CRUD e um sistema básico de autenticação.

🎯 Objetivo do projeto:

Criar uma API para gerenciamento de produtos, permitindo que usuários façam login e realizem operações de cadastro, consulta, atualização e exclusão de produtos.

🏗️ Visão geral do projeto

Nossa aplicação será composta por três partes principais:

  • API — responsável por receber as requisições HTTP e retornar respostas.
  • PostgreSQL — responsável por armazenar os dados.
  • Autenticação — responsável por identificar usuários e proteger determinadas rotas.

from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column
from sqlalchemy import String, Float
class Base(DeclarativeBase):
     pass
class Usuario(Base):
     __tablename__ = "usuarios"
     id: Mapped[int] = mapped_column( primary_key=True)
     email: Mapped[str] = mapped_column( String(150), unique=True)
     senha: Mapped[str] = mapped_column( String(255))
class Produto(Base):
     __tablename__ = "produtos"
     id: Mapped[int] = mapped_column( primary_key=True)
     nome: Mapped[str] = mapped_column( String(100))
     preco: Mapped[float] = mapped_column(Float)

🎫 Token JWT

Depois de validar as credenciais, a API pode gerar um token JWT. O cliente utiliza esse token nas próximas requisições protegidas.

Fluxo:

1. Usuário envia e-mail e senha.

2. API verifica as credenciais.

3. API gera um token.

4. Cliente armazena o token.

5. Cliente envia o token nas próximas requisições.

📡 Enviando o token

Normalmente o token é enviado no header Authorization utilizando o esquema Bearer.

request.http
1
2
3
GET /produtos
Authorization: Bearer <token>
🔐 Atenção:

JWT não deve ser tratado como uma senha.

Tokens precisam possuir validade adequada e a aplicação deve utilizar HTTPS em ambientes reais para proteger as credenciais e os tokens durante o transporte.

🔒 Senhas

Senhas de usuários nunca devem ser armazenadas diretamente no banco de dados em texto puro. Devemos utilizar uma função de hash apropriada para armazená-las de forma segura.

❌ Nunca faça:

senha = "123456"

e salve esse valor diretamente no banco.

✅ O correto:

Armazenar um hash seguro da senha e comparar a senha fornecida utilizando uma biblioteca apropriada.

📡 Status codes

Nossa API deve utilizar códigos HTTP apropriados para informar o resultado das operações.

  • 200 — requisição realizada com sucesso.
  • 201 — recurso criado.
  • 204 — operação realizada sem conteúdo na resposta.
  • 400 — requisição inválida.
  • 401 — usuário não autenticado.
  • 403 — acesso não permitido.
  • 404 — recurso não encontrado.
  • 500 — erro interno do servidor.

🧪 O projeto como QA

Este projeto reúne vários conceitos importantes para quem trabalha com QA e automação. Podemos testar não apenas os endpoints, mas também a integração entre API e banco de dados.

  • Validar códigos de status HTTP.

  • Testar campos obrigatórios.
  • Testar dados inválidos.
  • Testar autenticação.
  • Testar acesso sem token.
  • Validar persistência no PostgreSQL.
  • Testar criação, atualização e exclusão.
